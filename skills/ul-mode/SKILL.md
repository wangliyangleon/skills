# ul-mode

每次修改代码时，依次遵循：

- **First Make it Work：先实现功能。**
- **Then Make it Right：再改善质量。**
- **Follow Practice：遵守交付纪律。**

目标是写出正确、清晰、易修改的代码，保持与当前需求相称的复杂度。

## First Make it Work

### 以当前需求为边界

只实现已确认的需求及其必要依赖。不为假想的未来功能预建接口、配置项、扩展点或通用框架。

### 先理清数据，再组织逻辑

先明确核心数据、状态和约束。通过清晰的数据结构和类型减少无效状态及补救逻辑，命名统一使用业务术语。

### 优先选择直接的实现

让读者能够顺着代码理解主要流程。根据职责和复杂度拆分代码，不为短函数、少行数或设计模式增加间接层。

### 添加之前，先尝试删减

先检查能否通过删除冗余分支、过时逻辑、重复状态或特殊处理解决问题。避免叠加补丁，清理范围限于当前变更涉及的代码。

### 尊重现有设计，必要时调整

现有结构能自然容纳需求时，保持原样。需求暴露结构问题时，先明确合理设计，再分步落实，避免扩大为无关重写。

### 明确边界，减少状态负担

在数据入口完成必要校验与转换，内部遵循已建立的约束。分离业务计算与读写操作，减少共享可变状态；涉及重试或并发时，明确重复执行和写入冲突的处理方式。

### 优先扩展已有测试

修改前先找到所属的业务测试模块和已有 case。同一行为的变体优先补充数据、参数化场景或相关断言；已有覆盖足够时只运行验证。仅在独立业务行为无法清晰纳入时新增 case，新增文件更应克制。

### 修复根因，小步验证

先复现并定位问题，必要时用最小失败用例开展 TDD。每完成一个小单元就验证；连续修复失败时重新检查共同假设，不用吞异常、默认值或额外判断掩盖错误。

## Then Make it Right

### 一条业务规则只维护一处

同一规则集中维护。代码外观相似不代表需要抽象；只有表达同一概念、需要一起变化时才合并，确保抽象降低理解和修改成本。

### 测试体现业务契约

每个 case 围绕一个连贯行为，验证用户或调用方可观察的结果、状态及错误语义，避免绑定实现细节。保留有效回归保护，不为减少数量合并无关行为，也不为覆盖率制造测试。

### TDD 用例在交付前归位

将临时用例的场景与关键断言整合进所属模块的已有 case，确认仍能发现原缺陷或缺失行为，再删除临时或重复用例；保护独立契约且不宜合并的，保留为正式测试。

### 适度整理，及时停止

功能通过后，检查命名、重复、嵌套、死代码和不必要的抽象。重构保持既有行为并完成验证；需求已满足、代码已清晰时停止，不强制追求特定工具或机械指标。

## Follow Practice

### 保持文档克制

不自动创建过程日志、设计报告、总结文档或术语表。只有影响使用或后续维护的必要信息才写入文档，并优先更新已有内容。

### 简洁报告交付结果

过程更新只说明重要进展或阻塞。最终仅简要说明实现结果、验证结果和未解决事项，不逐项复述操作。

### 保护上下文窗口

主线程保留目标、约束、关键结论和当前状态。大量检索结果、原始输出和中间材料按需读取，处理后保留摘要，避免反复载入或粘贴全文。

### 安全清理工作区

在任务授权范围内清理临时文件和不再使用的 worktree，释放磁盘前确认没有依赖仍在使用它们。未提交或归属不明的工作保留，等待明确决定。

### 小步提交，明确依据

在已获提交授权时，按逻辑单元形成小而有序、可验证的提交。每次提交说明修改原因、具体变化和验证方式；推送及合入主线按当前任务授权执行。
